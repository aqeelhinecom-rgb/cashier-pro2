# Cashier Pro — تقرير حل تعارض المخزون وتعدد الأجهزة دون اتصال (المرحلة 14)

**وثيقة التقرير**: `docs/PHASE14_INVENTORY_CONFLICT_REPORT.md`  
**تاريخ التنفيذ**: نوفمبر 2026  
**طبيعة المرحلة**: حل تعارض المخزون في المبيعات غير المتصلة (Offline Inventory Conflict Resolution).  
**حالة قاعدة الإنتاج**: قاعدة **Dexie IndexedDB (`CashierPro_DB`)** محفوظة ولم تُمس، ولم يتم تفعيل Firebase على بيانات المحل الحقيقية، وتم تنفيذ كافة الاختبارات في بيئة محاكاة مستقلة تماماً.

## 2. مقارنة التصميم السابق والتصميم الجديد (Architecture Evolution)

```
┌────────────────────────────────────────────────────────────────────────────────┐
│                       التصميم السابق (قبل المرحلة 14)                           │
├────────────────────────────────────────────────────────────────────────────────┤
│ رصيد المخزون = رقم واحد مطلق (qty).                                            │
│ عند بيع الصنف دون اتصال من جهازين:                                             │
│ الجهاز A يخصم 2 من 2 -> المخزون = 0.                                           │
│ الجهاز B يخصم 2 من 0 -> إما يثبت المخزون عند 0 صامتاً، أو يهبط لسالب (-2).      │
│ النتيجة: ضياع الحقيقة المحاسبية، أو تشوه الجرد الفعلي للمحل دون علم الإدارة.   │
└────────────────────────────────────────────────────────────────────────────────┘
                                       │
                                       ▼
┌────────────────────────────────────────────────────────────────────────────────┐
│                        التصميم الجديد (المرحلة 14 المعتمدة)                     │
├────────────────────────────────────────────────────────────────────────────────┤
│ 1. فصل مستويات الرصيد الأربعة في نموذج مستقل (InventoryBalance):                │
│    • physicalStock: الرصيد الفعلي المتواجد فعلياً على الرفوف.                  │
│    • availableStock: الكمية المتاحة للبيع الفوري.                              │
│    • reservedStock: الكمية المحجوزة في فواتير معلقة.                           │
│    • conflictDeficit: العجز الصريح الناتج عن البيع المتزامن دون رصيد.          │
│ 2. عدم إخفاء العجز: يظل العجز مكشوفاً ومحسوباً بدقة (+3 قطع عجز).              │
│ 3. وسم الفواتير المتعارضة بـ (reconciliation_required: true).                  │
│ 4. سجل تسوية إدارية مستقل (ReconciliationRecord) بجميع بيانات الواقعة الرقابية.│
│ 5. حماية Idempotency لمنع تكرار القيود أو مضاعفة العجز عند إعادة إرسال الحزم.  │
│ 6. تسوية العجز آلياً عند وصول شحنة توريد جديدة (Restock) أو إرجاع بضاعة.       │
└────────────────────────────────────────────────────────────────────────────────┘
```

2. **`src/services/sync/inventoryConflictEngine.ts`**:

3. **`scripts/run-phase14-inventory-conflict.ts`**:
   - الجناح الاختباري المنعزل لتنفيذ سيناريوهات الاختبار العشرة والتحقق الرياضي التام.
