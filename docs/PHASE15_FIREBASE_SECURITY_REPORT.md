# Cashier Pro — تقرير تحصين أمان Firebase واعتماد الأجهزة (المرحلة 15)

**وثيقة التقرير**: `docs/PHASE15_FIREBASE_SECURITY_REPORT.md`  
**تاريخ التنفيذ**: نوفمبر 2026  
**طبيعة المرحلة**: تحصين أمان قواعد Firestore & Storage ومعالجة الملاحظة **SEC-01** الخاصة باعتماد الأجهزة والبيانات المالية.  
**حالة قاعدة الإنتاج**: قاعدة بيانات **Dexie IndexedDB (`CashierPro_DB`)** محفوظة كمصدر وحيد للحقيقة ولم تُمس، ولم يتم تفعيل Firebase على بيانات المحل الحقيقية، وتم تنفيذ واختبار كافة القواعد في بيئة تجريبية معزولة ومستقلة تماماً.

## 1. التدقيق الأولي والوضع السابق للملفات (Baseline Audit)

قبل إجراء أي تعديل أمني، تم فحص الوضع السابق:

1. **`firestore.rules` (الإصدار السابق)**:
   - كان يحتوي على دالة `isAuthorizedDevice(storeId, deviceId)` في السطر 50، ولكنها **لم تكن مستدعاة إطلاقاً** داخل كتل إنشاء الفواتير (`match /invoices`) أو المنتجات أو طابور المزامنة!
   - كانت الفواتير تسمح بالإنشاء بمجرد التحقق من `isStoreMember(storeId)`، مما جعل النظام عرضة لهجمات في حال تسريب توكن مستخدم واستخدامه من جهاز غير مسجل أو جهاز مسروق/ملغى.
   - كانت أسعار التكلفة موجودة في نفس وثيقة المنتج، مما صعّب عزل سعر التكلفة عن الكاشير سحابياً.
2. **`firebase-blueprint.json` (الإصدار السابق)**:
   - كان يفتقر إلى كيان مستقل لعزل التكاليف السرية (`ProductCost`)، وسجل التسويات الإدارية (`ReconciliationRecord`)، ودفتر المدفوعات غير القابل للتعديل (`Payment`).
3. **غياب قواعد Storage (`storage.rules`)**:
   - لم تكن هناك قواعد أمان مخصصة لـ Firebase Storage لحماية صور المنتجات والنسخ الاحتياطية من التلاعب أو الرفع العشوائي.

## 2. نموذج اعتماد الأجهزة والصلاحيات الجديد (Device Authorization & RBAC Architecture)

```
┌────────────────────────────────────────────────────────────────────────────────┐
│                        نموذج التحقق الثنائي الصارم (Zero-Trust)                 │
├────────────────────────────────────────────────────────────────────────────────┤
│ لا تُقبل أي عملية مالية أو مخزنية سحابية إلا بتحقق متزامن من عنصرين:           │
│                                                                                │
│ 1. هوية المستخدم الموثقة: (request.auth.uid) + التحقق من دوره وعضويته في المتجر │
│ 2. هوية الجهاز المعتمد الموثوق: (incoming().deviceId)                          │
│    يجب أن يتطابق مع وثيقة رسمية في Firestore:                                 │
│    /stores/{storeId}/devices/{deviceId}.status == 'active'                     │
│                                                                                │
│ ⚠️ لا يعتمد الخادم على أي قيمة يرسلها العميل (مثل isAuthorizedDevice: true)    │
│    بل يفحص قاعدة البيانات مباشرة لمنع أي تزوير أو تلاعب من جهة العميل.        │
└────────────────────────────────────────────────────────────────────────────────┘
```

### هرمية الأدوار السحابية المعتمدة (Server RBAC Roles):
1. **المالك (`owner`)**: كامل الصلاحيات، إضافة المتاجر، تعيين الأدوار، حذف الأجهزة، واستعادة النسخ الاحتياطية.
2. **المدير / المشرف (`admin` / `manager`)**: إدارة المنتجات، إلغاء الفواتير (Void)، تسوية العجز المخزني، وإدارة الأجهزة.
3. **المحاسب (`accountant`)**: الاطلاع على أسعار التكلفة والأرباح، ومراجعة سجلات الفواتير والدفعات وسجلات التسوية.
4. **مسؤول المخازن (`inventory_manager`)**: إضافة الأصناف، تعديل الكتالوج، وإدخال شحنات التوريد (Restock).
5. **الكاشير (`cashier`)**: إنشاء فواتير البيع من جهاز معتمد فقط، **حظر قراءة أسعار التكلفة**، **حظر إلغاء الفواتير دون إشراف**، و**حظر تعديل الدفعات**.

## 3. مقارنة القواعد القديمة بالقواعد الجديدة المحصنة (Rules Delta)

| المسار والكتلة | القواعد القديمة (قبل Phase 15) | القواعد المحصنة الجديدة (Phase 15) | الأثر الأمني المتحقق |
|---|---|---|---|
| **اعتماد الأجهزة** | دالة مهملة لا تُستدعى في مسارات الكتابة. | إلزامية `isAuthorizedDevice(storeId, incoming().deviceId)` في الفواتير والدفعات والمخزون وطابور المزامنة. | سد ثغرة SEC-01 وحظر أي جهاز غير مسجل أو ملغى (Revoked). |
| **سرية التكلفة** | كانت التكلفة `buy_price` مدمجة في وثيقة المنتج ومتاحة لقراءة الكاشير. | فصل التكلفة في مسار مستقل `/stores/{storeId}/products_cost/{productId}` مقصور على المحاسب والمدير والمالك. | منع الكاشير من استكشاف أرباح المتجر وأسعار التكلفة عبر السحابة. |
| **الفواتير** | كانت تسمح بالكتابة لأي عضو في المتجر، وتسمح بتعديل الفاتورة للمدير دون قفل الأرقام. | قفل الأرقام المالية: `incoming().total == existing().total && incoming().paid == existing().paid`. | منع التلاعب بالمبالغ المالية للفواتير المعتمدة نهائياً. |
| **الدفعات المالية** | لم يكن هناك قفل صريح على منع التعديل. | إضافة `/payments/{paymentId}` مع `allow update, delete: if false`. | تحويل سجل المقبوضات والدفعات إلى دفتر أستاذ غير قابل للتعديل (Immutable Ledger). |
| **سجل التسويات** | غير معرف في القواعد السابقة. | إضافة `/reconciliation_records/{recordId}` محمي من تعديل الكاشير. | حماية قيود عجز المخزون من الإخفاء أو التلاعب غير المصرح به. |
| **الحذف الفيزيائي** | قواعد متفرقة. | قفل شامل: `allow delete: if false` على المتاجر والفواتير والمنتجات والدفعات والتسويات. | منع هجمات مسح البيانات عبر واجهات REST API المباشرة. |

## 4. نتائج اختبارات الهجمات الـ 14 (Security Attack Vectors 14/14)

تم تشغيل اختبارات الهجمات الأمنية المباشرة في `scripts/run-phase15-security-hardening.ts` لمحاكاة محاولات الاختراق عبر REST API أو التوكنات المسربة:

| # | سيناريو الهجوم الأمني المختبر | النتيجة المتوقعة | النتيجة الفعلية | آلية الحظر وسبب الرفض |
|:---:|---|:---:|:---:|---|
| **1** | مستخدم من متجر A يحاول قراءة بيانات متجر B | **DENIED** | **DENIED** ✅ | رفض الوصول لعزل المستأجر التام (`isStoreMember`). |
| **2** | جهاز غير مسجل بالنظام يحاول إنشاء فاتورة | **DENIED** | **DENIED** ✅ | حظر SEC-01 لعدم وجود الجهاز في سجل الأجهزة المعتمدة. |
| **3** | جهاز ملغى تفعيله (Revoked) يحاول كتابة فاتورة | **DENIED** | **DENIED** ✅ | حظر فوري لكون حالة الجهاز `status == 'revoked'`. |
| **4** | كاشير يحاول قراءة أسعار التكلفة وأرباح النظام | **DENIED** | **DENIED** ✅ | رفض الوصول للمسار المحمي `products_cost` لرتبة الكاشير. |

| **6** | عميل يحاول حذف فاتورة نهائياً عبر DELETE HTTP | **DENIED** | **DENIED** ✅ | رفض قاطع بسبب `allow delete: if false`. |

| **10** | محاولة إرسال `isAuthorizedDevice: true` لتخطي الفحص | **DENIED** | **DENIED** ✅ | فشل الخداع؛ الخادم يفحص قاعدة البيانات ولا يثق بحمولة العميل. |

| **12** | كاشير يحاول تعديل سجل تسوية العجز لإخفائه | **DENIED** | **DENIED** ✅ | قصر تسوية العجز وتعديل السجلات على المدراء والمالك. |
| **13** | مستخدم من متجر A يحاول رفع ملف في مسار متجر B | **DENIED** | **DENIED** ✅ | رفض الوصول لمسارات التخزين الخاصة بالمتاجر الأخرى. |

## 5. قواعد تخزين الوسائط والصور المعتمدة (`storage.rules`)

تم إنشاء ملف `storage.rules` لحماية وسائط التخزين السحابي:
1. **عزل المستأجرين**: المسار المسموح به مقيد بـ `/stores/{storeId}/products/{imageId}`.
2. **حدود الحجم الصارمة**: الحد الأقصى لصورة المنتج هو **2 ميجابايت (2MB)**، والحد الأقصى للنسخة الاحتياطية هو **100 ميجابايت (100MB)**.
3. **التحقق من النوع والامتداد**: التحقق من `request.resource.contentType.matches('image/(jpeg|png|webp)')`.
4. **حظر الحذف العشوائي**: حظر حذف ملفات النسخ الاحتياطية سحابياً من قبل العملاء.

## 7. المخاطر المتبقية والتوصيات (Residual Risks & Recommendations)

1. **إلغاء أجهزة الكاشير وتزامن الجلسات (Revocation Latency)**:
   - بفضل فحص `isAuthorizedDevice` المباشر في قواعد Firestore عند كل عملية كتابة، يتم إيقاف أي جهاز ملغى فورياً في السحابة حتى لو كان يحتفظ بـ User Token نشط.
2. **تنبيه إداري في لوحة التحكم**:
   - التوصية بإظهار إشعار فوري للمدير عند رفض السحابة لأي طلب قادم من جهاز يحمل كود `unauthorized_device` لتنبيه الإدارة بمحاولات الاختراق أو الأجهزة المفقودة.
